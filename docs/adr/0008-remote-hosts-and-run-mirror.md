# Remote hosts are reached by an app-managed SSH tunnel and their runs are mirrored locally

The app side of [ADR 0007](0007-remote-agent-daemon.md): how a profile runs on another machine, and how that run shows up in the app. User guide: [remote hosts](../features/remote-hosts.md).

Decisions that are not obvious from the code:

- **The system `ssh`, no SSH library, no credentials.** The tunnel is `ssh -N -L <local>:<remote>` with `BatchMode=yes` (it can never prompt), `ExitOnForwardFailure`, keep-alives, and `ControlMaster=no`/`ControlPath=none` so the forward belongs to, and dies with, the process the app owns. A host stores an SSH alias and the daemon's endpoint, nothing else; a `direct` (url + token) type is reserved in the schema and not implemented. A remote socket is forwarded to a local unix socket in a private, owner-checked directory; a port endpoint (or a platform without unix sockets) uses a loopback port.
- **State reads never wait for a connection.** The per-host lock is held across an ssh connect (seconds); the state, address and ssh pid are published in a separate view, so the UI commands, `forget` and the app exit return at once (a forgotten host's connect is cancelled and its ssh killed).
- **On demand, kept alive while used, never retried by a launch.** The tunnel opens on first use. A monitor thread health-checks `/v1/info` and restarts a failed tunnel with a backoff (2 s doubling to 60 s). A launch that finds the host unreachable fails at once with `host_unreachable` and the user relaunches; only the monitor and the mirror retry. Connection state is emitted to the UI (`host-state`).
- **A protocol mismatch is a sticky state, not the `enabled` flag.** The user's on/off switch is not rewritten behind their back; the host shows *protocol mismatch* with both versions until "Test connection" sees a matching one. Nothing is sent to it meanwhile.
- **Remote chats are deferred to S10.** A review chat keeps a session and edits a local worktree; `/v1/oneshot` has no session support, so a remote chat needs session endpoints in the worker API first. Until then a remote profile is refused for chat and for interactive sessions (also in the feature mapping), and cannot be the default profile (the default serves chat, sessions and system routines).
- **A host with active runs cannot be repointed.** Changing its SSH target or endpoint is refused while runs are queued or running, because the mirror follows `remote_run_id` on that host's daemon.
- **`RemoteHarness` is a `Harness`, but only for one-shots.** Profiles resolve to `&'static dyn Harness`, so a profile with a host resolves to a cached `RemoteHarness` per (host, harness). It keeps the local harness' id and name (usage and the UI group by harness; the host is a separate column) and reports the host's capabilities with sessions, resume, fork and interactive use switched off, because protocol 1 has no endpoints for them. Anything the wire cannot carry (a session, a native permission mode, harness-native extra args) is refused with a message, never silently dropped. Local-only work (review chats, interactive sessions, system routines) refuses a remote profile through `Resolved::ensure_local`.
- **Remote routine runs bypass the local engine.** The run gets its `routine_run` row (with `host_id`, `remote_run_id`, `last_remote_seq`) and a worker thread; the local queue, concurrency cap, quit prompt, exit kill and restart interruption all ignore rows with a host (they filter on `host_id IS NULL`), because those runs outlive the app by design. The request is rendered in the app (prompt, neutral access and tools, workspace as `owner/name` + PR, a context snapshot of the card and its links, the review's focus); a context with no GitHub repository is refused.
- **The mirror writes the same rows a local run does.** Events are copied by `seq` with `INSERT OR IGNORE` (duplicates are free and not announced twice), progress is the max of the stored events and `last_remote_seq`, and the stream resumes `after_seq`. A dropped connection leaves the run `running` and reconnects with a backoff. At start-up and on reconnect every unfinished remote run is looked up again: still running, finished meanwhile (its events are caught up first), or unknown to the host (an explicit error). The idempotency key is derived from the row (`cr:<queued_at>:<id>`), so a crash between the post and the write-back re-posts and finds the same run.
- **Outbox ops are applied at least once, and once in practice.** `remote_applied_op` is keyed by `(run, op id)`. A sync fetches the unacknowledged ops, applies the unsettled ones through the same functions `cr` uses locally, records each, and acknowledges the contiguous settled prefix; a lost acknowledgement means the host sends the same ops again and the table makes the second application a no-op. The guarantee is at-least-once, not exactly-once: a crash (or a failed write to the table) between applying an op and recording it applies it again on the next sync. A failing op is retried at most once per 30 s (syncs run about once a second, and a short outage of `gh` must not use up the attempts) and given up on after three tries. A given-up op stays unacknowledged on the host while the run is live and is acknowledged only when the run ends; at that point it is listed in the run's error text and logged, so a dropped board write is never silent. Errors reading or writing the table are logged at error level.
- **Stopping goes to the host.** A stop request is sent on a worker thread (it may have to open the tunnel). If the host cannot be reached the run is settled locally as stopped with a message that it may still be running there.

## Considered Options

- Running remote runs through the local engine with a `RemoteHarness::spawn`. Rejected: the engine owns a process, a pid and files; a remote run is a row plus a stream, and forcing it through process control would need every engine path to special-case it.
- Setting `enabled = 0` on a protocol mismatch. Rejected: it confuses a user's choice with a diagnosis, and the state must clear itself when the host is updated.
- Embedding an SSH implementation. Rejected: the user's `~/.ssh/config`, agent and known hosts are what makes the connection work.
