# All AI calls go through one `Harness` trait; profiles select the harness

Every AI feature used to call the `claude` CLI directly, from about six places: the review chat, theme suggestions, session summaries (extract and fork), the routine manager, and three builders of interactive-session argv. Each had its own flag handling, so supporting a second CLI would have meant touching all of them.

`ai::Harness` (`src-tauri/src/ai/`) is the single seam, shaped like `provider.rs`: an object-safe, synchronous trait, an `ai::harness_for()` resolver, a compile-time object-safety assertion and a recipe comment for adding an implementation. `ai/claude.rs` (`ClaudeCode`) is the only code that builds a `claude` command line or parses Claude's output (the `-p` JSON envelope and the `stream-json` lines). Run events are stored twice: the raw line and a harness-neutral `norm` produced by `Harness::normalize`, so the transcript and the final status work for any harness.

Requests are neutral: tool policy, access level, session mode (ephemeral, new id, resume, fork), system prompt mode. Each harness translates them to its own flags. Capabilities are data (`Caps`), so the UI and routers can refuse unsupported combinations instead of failing mid-run.

Decisions that are not obvious from the code:

- **No behavior change when introduced.** Argv and env of every call site are pinned by snapshot tests that were written before the move. `Access::Native` passes a harness-native permission mode through verbatim because routines still store Claude's `permission_mode` strings; it goes away when profiles replace those columns.
- **`spawn` returns the `Child`, not a bare pid.** The run engine writes the prompt to stdin and polls and reaps the process, so a pid is not enough. Streaming still goes to files so a run can outlive the app.
- **Auth is delegated to each CLI.** The app stores no token and has no raw HTTP client. Model providers reachable through a CLI (for example OpenRouter via opencode) are reached through that CLI.
- **Profiles select the harness.** A profile names a harness plus model and settings (`ai_profile`, never a secret). A routine uses its own profile, else the profile mapped to its feature (`meta` rows `ai_profile.chat|summaries|theme|sessions`), else the default profile (`is_default`, at most one). A launch can override the model only. A missing or deleted profile falls back to the default; with no default the app runs Claude Code with the legacy env-based model resolution, so Bedrock setups keep working. `ai::profiles` holds storage and the resolver; `harness_by_id()` is the registry. Each run carries its own harness (`Prepared.harness`, stored in `routine_run.harness` for re-adoption); the engine's constructor harness is only the fallback.
- **Cheap built-in models stay cheap.** Summaries and theme suggestions ship their own fast model. The default profile's model never applies to them: only a profile mapped to that feature with a model of its own does.
- **Routines get a neutral access model.** `routine.access` (`read_only`, `edit`, `full`) is the primary setting; Claude's permission mode, allowed tools, extra args and system prompt mode move to `routine.harness_overrides` keyed by harness id. Migration 0043 backfills both from the old columns, which stay for one release (still written, no longer read) and are dropped later. A native permission mode wins over the access, so changing only the access drops a stale native mode. Before a launch, `ai::check_caps` refuses a routine whose access or tool needs exceed the harness `Caps`, naming the missing capability.
- **Routine kind.** `plain` or `system` (`system` = has a Rust handler). System routines run locally and expose only profile, model, timeout and enabled; their prompts and tools belong to the handler.
- **Chats pin their profile.** `chat.profile_id` is set when a session starts. Switching profile starts a new harness session and puts the earlier messages in the first turn's system prompt as a previous-conversation block capped at about 200 KB (oldest messages dropped first, with a marker line). Sessions are only resumed on the profile they started with.
- **opencode (`ai/opencode.rs`).** Verified against opencode 2.2.5. `opencode run --format json` has no final line (the run ends with a `step_finish` that is not `tool-calls`; usage and cost are per step), so `Harness::accumulates` makes the engine fold the last text and the summed usage over the stream. It has no system prompt flag (the prompt is prepended to the message) and wants session ids starting with `ses` (the app's UUIDs are mapped, deterministically). Streaming runs use `--standalone` so killing the process group stops the work. The access level picks the agent (edit: `build`, full: `build --auto`). opencode has no flag that denies bash (its `plan` agent only denies edits), so it does not offer read-only access and `check_caps` refuses read-only routines on it; the user picks Edit or Full knowingly or uses another profile. An explicit `agent` in the profile settings or `--agent` in `extra_args` overrides the access-derived agent (a `build` agent lets a routine edit), and nothing the app passes can take bash away. Runs that ask for no tools (summaries, theme) use `plan`, which is strictly less capable than the default agent.
- **Codex (`ai/codex.rs`).** Verified against codex-cli 0.167.0. `codex exec --json` prints `thread.started` (the session id), item events (`agent_message`, `command_execution`, `file_change`) and `turn.completed` with a `usage`, with no result line, so like opencode it folds the last message over the stream. Codex assigns its own session id and cannot pin one: `Caps.pins_session_id` is false, `TurnResult.session_id` and `Harness::session_of_line` carry the id Codex chose back to the chat row or the routine run, and card linking is skipped. `exec resume <id>` has no `-s`, `-C` or `--add-dir`, so on resume the sandbox and writable roots go in as `-c` overrides. `turn.completed.usage` is the total of the whole thread (a resumed turn reports the earlier turns too), so one-shot resumes subtract the thread's last `token_count` read from its log under `~/.codex/sessions`; a streamed resume is not corrected. Cached tokens are inside `input_tokens` and are split out. Codex reports no cost (`reports_cost` is false, the Usage tab shows tokens only). The approval policy is pinned to `never` (a non-interactive run cannot ask), and `--skip-git-repo-check` is always passed because the app picks the directory.
  - **What the access levels actually enforce.** Read-only and edit use Codex's OS sandbox (bubblewrap/landlock on Linux, seatbelt on macOS), checked with `codex sandbox`: in `read-only` every write fails with a read-only file system, so unlike opencode Codex offers real read-only access. It does not hide anything: the whole file system, including `~/.ssh` and other credentials, stays readable, and network access follows Codex's own default for sandboxed modes (off; not verified here). In `workspace-write` the writable roots are the working directory, `/tmp` and the extra directories (granted only in that mode); a linked git worktree's git dir is outside them, so `git commit` fails there unless the profile adds the git dir through `extra_args` (`--add-dir`). The app does not add it: it would also make `.git/hooks` writable, which is a sandbox escape. Read-only routines that need to write to their scratch directory fail by design; set them to edit.
  - **Full access.** Mapped to `danger-full-access` (no sandbox) and refused unless the profile's settings say `"allow_full": true` (off by default; the editor warns). The refusal happens when the command is built, because `check_caps` sees capabilities, not settings. A profile `sandbox` setting (`read-only`, `workspace-write`, `danger-full-access`) can only lower the access-derived mode, never raise it (deviation from S06, which lets the profile override: a profile must not widen what a feature asked for), and `danger-full-access` needs `allow_full`. `extra_args` may not carry anything that changes the sandbox or approvals: `--dangerously-bypass-approvals-and-sandbox`, `--yolo`, `--full-auto`, `-s/--sandbox`, `-a/--ask-for-approval`, `-p/--profile`, `-C/--cd`, `--enable`/`--disable` (feature flags reach approval and permission machinery), `--approve-for-me`, `--dangerously-bypass-hook-trust`, `--worktree`, `--ignore-rules`, `--ignore-user-config`, `-o/--output-last-message` (makes Codex write an arbitrary file outside the sandbox) and the internal `--cr-` markers. `-c/--config` is an allowlist, not a denylist: each key is parsed into dotted segments with quotes and whitespace stripped (so `"sandbox_mode"`, `'sandbox_mode'` and `sandbox_workspace_write . network_access` are seen for what they are), and only the single-segment keys `model`, `model_reasoning_effort`, `model_reasoning_summary`, `model_verbosity`, `hide_agent_reasoning`, `show_raw_agent_reasoning` and `personality` pass. Everything else is refused, notably `sandbox_mode`, `approval_policy`, `profile(s).*`, `sandbox_workspace_write.*`, `default_permissions` and `permissions.*` (checked against codex-cli 0.167.0 with `codex debug prompt-input`: a later `-c default_permissions=":workspace"` or `-c "sandbox_mode"=...` does override an earlier `-c sandbox_mode="read-only"`). The refusal is raised when a profile is saved and again when the command is built: the command is refused with an error, on new and resumed sessions alike. The internal markers `settings_args` uses carry a per-process secret, so `allow_full` can only come from the settings key. Network access in `workspace-write` is unverified, so the UI and docs do not promise it is off. `Access::Default` maps to read-only, so features that ask for no tools never write.
  - **`--add-dir` is validated, still a heuristic.** `--add-dir` stays allowed in `extra_args` (it is how a profile makes a linked worktree's git dir writable), as `--add-dir <p>` or `--add-dir=<p>`, but the value is checked on profile save and again at run time by one function: absolute (`~` is not expanded), no NUL or newline, lexically normalized (`..` may not escape the root), and, after resolving symlinks, not `/`, not the home directory or an ancestor of it, not under `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.config`, `~/.codex`, `~/.claude`, `/etc`, `/usr`, `/bin`, `/sbin`, `/boot`, `/proc`, `/sys` or `/dev`, and (at run time only) not the run's working directory or an ancestor of it; at run time it must also be an existing directory, while save accepts one that does not exist yet. A linked worktree's git dir (`<repo>/.git/worktrees/<name>`, `<repo>/.git`) passes. It is a deny list: other sensitive directories outside it pass, so the profile is still trusted configuration, and a passing `--add-dir` still adds writable roots in `workspace-write` (read-only mode ignores it). The app does not pass it on resume, where only its own `writable_roots` override applies.
  - **Resume and user config.** On resume the sandbox is `-c sandbox_mode=...` (no `-s` on `exec resume`). Checked against codex-cli 0.167.0 with a scratch `CODEX_HOME` and `codex debug prompt-input` (no model call): `-c sandbox_mode` beats `sandbox_mode`, `default_permissions` and `[profiles.*]` in the user's `config.toml`; a legacy `profile = "x"` there (or `-c profile=...`) is a hard error in this version, and the new `--profile` layers `<name>.config.toml` only when passed on the command line, which `extra_args` cannot do. So no profile can weaken a resumed sandbox here; older Codex versions with legacy profiles were not checked.
  - **Sessions.** Live sessions come from the process list (a `codex` TUI, not `exec` or `app-server`) plus the logs `~/.codex/sessions/YYYY/MM/DD/rollout-*-<id>.jsonl` (header line: id, cwd, originator). Codex writes a log on the first message and keeps no file open, so a `codex resume <uuid>` TUI is paired by id and an unpinned TUI only when it is the one unpinned TUI of its directory and an interactive log of that directory was written since it started; `codex exec` and desktop-app logs are never paired. Titles come from `session_index.jsonl`.
- **A chat's session belongs to the harness that started it.** `chat.session_harness` is recorded with the session; when the chat's profile resolves to another harness (a deleted pinned profile, a changed default) the turn starts a new session and replays the earlier messages, as for a profile switch.
- **Session discovery is per harness, Claude richest.** `Harness::live_sessions` returns the neutral `ai::AgentSession` (harness id, session id, cwd, live, title, with Claude-only fields optional). Claude keeps `claude_sessions.rs` (session files, `claude agents`, transcripts, hook summaries); the Sessions view merges the other harnesses' live sessions (basics only, no attach, stop or summaries). Interactive launches take the `sessions` profile's harness, or the one picked on the menu. Card linking records `claude_session` for Claude and an `ai_session` row tagged with the harness (migration 0046) for a harness that can pin a session id; for others nothing is recorded.

## Considered Options

- A raw HTTP client for API-key models. Rejected: it would make the app store tokens and re-implement tool use, session handling and cost reporting that the CLIs already provide.
- An enum of harnesses instead of a trait. Rejected: `provider.rs` already uses a trait for the forge, and a trait lets a remote wrapper implement the same interface later.
